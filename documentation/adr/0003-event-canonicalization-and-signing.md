# ADR 0003: Event canonicalization and signing

- **Status:** Accepted
- **Date:** 2026-09-27
- **Work package:** [#1651](https://openproject.niew.dev/work_packages/1651)

## Context

ADR 0001 fixes that events are signed with Ed25519 over the RFC 8785 (JCS)
canonical form of the event without `publisher.signature`, and that a node's
libp2p peer ID is derived from the same key. Any implementation must produce
byte-identical canonical forms, or signatures will not verify across nodes.
Receivers must authenticate an event without looking up keys.

Two pieces are needed: a JCS implementation and the conversion between an
Ed25519 key and its peer ID.

## Decision

- **JCS is implemented in-house** in `pkg/obieproto/internal/jcs` (about 300
  lines) rather than imported: the algorithm is small, the RFC is precise and
  ships test data, and we want the strict input rules below, which
  general-purpose JSON libraries do not enforce. It follows RFC 8785 fully
  — ECMAScript number serialization, minimal string escaping, object keys
  ordered by UTF-16 code units — and is tested against the RFC's examples and
  appendix B numbers.
- **Strict I-JSON input:** invalid UTF-8, lone surrogates, duplicate keys,
  non-finite numbers and integer literals beyond ±(2^53−1) are errors, never
  repaired. Otherwise two different events could share one signature (for
  example `encoding/json` turns invalid UTF-8 into U+FFFD, and an `int64`
  beyond 2^53 loses precision as a double). `CanonicalBytes` checks event
  strings for valid UTF-8 before marshalling for the same reason.
- **Signed bytes:** `json.Marshal(event)`, parsed generically, with
  `publisher.signature` removed, then JCS-encoded. Deriving the form from the
  struct's JSON encoding keeps it in step with the wire format; a
  hand-written struct encoder would have to track every field change. For
  speed, the JSON is parsed with `encoding/json` (it is known to be valid
  I-JSON) instead of the strict JCS parser used for foreign input.
- **Peer IDs:** the libp2p legacy base58btc form of an identity multihash of
  the protobuf `PublicKey{Type: Ed25519, Data: key}` (`12D3KooW…`). It is
  implemented directly with `github.com/mr-tron/base58` (already in the
  module graph via go-multiaddr) and cross-checked with go-libp2p. We do not
  import go-libp2p for this; the mesh work package will, and must produce
  the same IDs. `PublicKeyFromPeerID` accepts only exactly this encoding.
- **API:** `Sign(event, key)` fails with `ErrPublisherMismatch` unless
  `publisher.peer_id` is the key's peer ID. `Verify(event)` takes the key from
  the peer ID: a peer ID without an embedded Ed25519 key is
  `ErrPublisherMismatch`; a missing, malformed or non-matching signature is
  `ErrInvalidSignature`. Ed25519 cannot tell a tampered event from a
  signature by another key, so both are `ErrInvalidSignature`.
- **Separation of concerns:** `Sign` and `Verify` do not apply the obie/0.1
  field rules, and `Decode`/`Validate` check only the signature's format.
  Receivers call both.
- **Test vectors** in `documentation/spec/test-vectors/` are generated by the
  package's tests (`go generate ./pkg/obieproto`) and compared on every test
  run. The tests also check each file independently of the generator.

## Consequences

- Changing the event's JSON encoding (a new field, a renamed key, a changed
  `omitempty`) changes the signed bytes. It is a protocol change, shows up as
  out-of-date test vectors, and needs a new spec version.
- Integer fields of an event must stay within ±(2^53−1) to be signable.
- Verification costs about 60 µs per event on one core (about 17k
  events/s on a Ryzen 9 7950X3D). Two-thirds of that is Ed25519 itself.
